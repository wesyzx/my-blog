Theme Proposal / 轨道之外

墨白

把界面颜色归零，让照片和排版说话。这份方案从 song.al（Typlog 的 ueno 主题）拆出一套可以照抄的克制逻辑，再按「轨道之外」现有的八个栏目重新组装 —— 不是换一层皮，是换一套判断标准。

参考站点song.al · ueno 0.6.3
适配架构8 个页面 / 4 个导航组
核心变化颜色归零 · 图片主导
改动范围globals.css + 4 个组件

灵感来源：song.al 到底好在哪

先把参考对象拆开。下面是 song.al 的真实页面（左：首页列表，右：关于页），以及你现在的站点。三张图放在一起，差异一眼可见。

拆解：ueno 主题的 14 个决定

一句话总结：ueno 的高级感不来自任何一处花哨的设计，而来自「把颜色和装饰全部撤掉，只留排版和照片」。它敢让整页只有黑白灰，是因为照片足够好看 —— 这一点对以相册、美食、旅行为主的「轨道之外」同样成立。

两条不能照抄的地方

1. 正文衬线不能直接用 Merriweather。它没有中文字形，落到 CJK 时会退回系统衬线，中英字重和字面不匹配。你的站点已经引了 Noto Serif SC，保留它，只在西文部分加 Source Serif 4 打头。

2. 左栏不是作者卡，是导航。song.al 左栏只列 6 个外链，所以能做得极简；你有 4 个导航组、8 个页面，直接照搬会把功能弄丢。方案是：保留分组导航，但把品牌、主题切换搬进左栏，桌面端取消顶部导航条 —— 这才是 song.al「左栏常驻」结构的真正价值。

02 / Principles

五条设计原则

后面所有的具体数值，都是从这五条推出来的。改稿时如果拿不准，回到这里判断。

原则具体含义落到你的站点
① 颜色归零 界面只用无彩灰阶，唯一强调色是墨黑。所有颜色由照片提供。 删掉 --color-accent 的深绿、--color-warm 的暖棕、body 的网格纹理；图标、标记点、热力图全部去色。
② 图片是主角 有封面的内容用大图卡；没封面的用纯文字行。缩略图不再当「配菜」。 首页「最近留下」、博文列表改成 2.35:1 封面卡；相册封面从 3:2 放大；美食卡去掉细边框。
③ 层级靠排版 字号 / 字重 / 灰度三档定层级，不靠色块和彩色边框。 页面标题、栏目标题改用无衬线 600；正文 17.5px 衬线；元信息 11px 大写灰。
④ 边框收敛 圆角 2px、图片 3px，阴影只留浮层一处，其余靠 1px 细线。 控件圆角 6px → 3px；图片 4px → 3px；卡片边框改为「只在需要时出现」。
⑤ 两个签名元素 全站只保留两个反复出现的装饰：4px 竖条 + 100px 短横线。 取代现在的 .page-header::after 42px 绿色短线；正文分隔用短横线而非通栏细线。

B. 强调色：三选一

强调色的出场位置是固定的，全站只有 5 处：正文链接的下划线、当前导航项、悬停态、热力图最高档、地图标记点。它不该出现在任何大面积色块上。

#000000 浅
方案 A · 纯墨推荐

完全对齐 song.al。界面里没有任何「颜色」，只有深浅。照片成为唯一的色彩来源，观感最干净、最耐看，也最不会过时。

#2f4a2b 浅
方案 B · 墨绿

保留站点现有的绿色基因，但把明度压到很深、饱和度降到接近灰。远看几乎像黑，只在细线和 hover 时才透出一点绿。

#8a4a2c 浅
方案 C · 暖赭

保留「美食」栏目的暖棕，并把它提升为全站强调色。整体偏暖，与旅行、食物主题契合，但会比 A 少一分冷静。

为什么当时推荐 A：你现在同时用了深绿（主强调）和暖棕（美食专属）两种色相 —— 两套彩色系统会让界面看起来「有想法但没统一」。归零之后，即使以后想加回颜色，也只需要改一个变量，且立刻能判断出好不好看。

⚠️ 补充（见第 10 节）：这一条后来被推翻了。纯墨方案的实际观感偏冷 —— 照片是主因，但「冷灰 + 纯黑 + 纯白」这套 token 本身也贡献了不少。如果你在意温度，方案 C 暖赭 #8a4a2c 更合适，配合暖灰阶使用。第 10 节给了完整的暖化 token 和三档暖度选择。

C. 明暗模式对照

深色模式不是「把颜色反过来」，而是重新选一组值。要点：深色下强调色要退成中灰（#b4b4b4），不能用纯白 —— 纯白在深底上会跳出来抢标题的注意力，而 ueno 用 #6c6e79 又太暗，读不清。

04 / Typography

字体与排版

这是本方案里第二个大改动：栏目标题从衬线改成无衬线。song.al 全站标题都是无衬线，这带来的现代感，比配色更容易被感知。

字体栈

--font-sans: -apple-system, BlinkMacSystemFont, "MiSans", "PingFang SC",
             "Hiragino Sans GB", "Microsoft YaHei", system-ui, sans-serif;
--font-serif: "Source Serif 4", "Noto Serif SC", "Songti SC", STSong, serif;
--font-mono: ui-monospace, SFMono-Regular, Menlo, Monaco, Consolas, monospace;

/* 现有写法：--font-zh 里 MiSans 排第一，且 --font-sans = --font-zh
   新方案把系统字体提到最前：中文本地字体（PingFang）比网络字体
   MiSans 渲染更稳，也少一次 300KB 的字体请求。 */

谁用衬线、谁用无衬线

位置字体为什么
站点 UI（导航、按钮、标签、元信息）无衬线小字号下衬线会糊，无衬线更清晰
栏目标题（博文 / 相册 / 关于…）无衬线← 本次改动。song.al 的做法，干净利落
列表标题（封面卡 / 文字行）无衬线与栏目标题统一，让「正文」成为唯一衬线区
首页 hero、侧栏诗句衬线这两处是「文学性」的，保留书卷气
文章标题、文章正文、图注衬线长文阅读用衬线，中文尤其明显

字号阶梯

把日子写下来hero · 38 / 600 / 1.32
文章标题article h1 · 32 / 700 / 1.36
栏目标题page h1 · 27 / 600 / 1.3
封面卡标题cover card · 23 / 500 / 1.35
文字行标题text row · 17 / 500 / 1.45
正文段落十七点五像素body · 17.5 / 400 / 1.85
导语与摘要文字lead · 15 / 300 / 1.8
EDITORIAL METAmeta · 11 / 600 / .12em 大写

中英混排三条规则

1. 数字一律等宽。序号、日期、热力图、运动统计都用 --font-mono。等宽数字在列表里能对齐成一条线，是「编辑部感」的关键。

2. 中文强调用着重号，不用斜体。这是 ueno 已经在做的事：text-emphasis: filled dot。中文没有斜体字形，强行倾斜是伪斜体。效果：这就是中文强调的正确写法。

3. 开启中英自动留白。text-autospace: ideograph-alpha ideograph-numeric，让「在 Notion 里」这类混排自动有呼吸。一行 CSS，效果立竿见影。

为什么敢删顶栏：你的左栏已经是一个完整的导航（4 组 + 关于），顶栏那 4 个栏目和它是重复信息。删掉顶栏后，页面从「应用」变成「刊物」—— 这是 song.al 和绝大多数个人博客的分水岭。

旅行

在北海道的秋天，遇见一场早雪

2026.09.088 分钟阅读 · 北海道 · 道东

十月的道东已经落过两场雪。这次没有做太详细的计划，只是想看看北方的秋天到底有多短 —— 结果它比我想象的还要短，短到只有一周。

从钏路出发，沿着海岸线一路向东。车窗外的颜色在不断变化，从深绿到枯黄，再到一片安静的白。司机说这是今年第一场雪，比往年早了十天。

雪落下来的时候没有声音，只有海还在响。那一刻我忽然明白，为什么有人愿意在这么冷的地方住一辈子。

关于路线

整条线路大约 320 公里，建议留三天。如果只在秋天来，十月中旬是最稳的窗口期。详细的路书我整理在这篇笔记里了，包含每一段的加油站和休息点。

回来之后整理照片，发现拍得最多的不是雪，而是那些空无一人的公路。也许旅行的意义从来不在目的地，而在于你终于有时间什么都不想。

09 / Rollout

落地清单

按「先看见变化、再动结构」的顺序分三批。每批做完都能独立上线，不需要等全部改完。

第一批 · 换色与去装饰改动小，效果最大
  1. 替换 app/globals.css 的 :root 与 [data-theme="dark"] 两个 token 块（用上面的代码）
  2. 删除 body > main 的网格纹理那一行
  3. 把 .page-header::after 的 42px 绿短线换成标题左侧的 4px 竖条
  4. 删除 .page-icon 组件（绿底图标）以及各页面里对它的引用
  5. .food-card / .food-meta-location 里的 --color-warm 换成 --text-3
第二批 · 字体与结构观感分水岭
  1. --font-sans 把系统字体提到最前，MiSans 退到后备
  2. .page-title / .home-section-title / 列表标题改用 --font-sans
  3. 桌面端 .site-header 设 display: none，品牌与主题切换搬进 SiteSidebar.tsx
  4. .site-frame 改两栏 232px + 820px，删掉 .site-breathing-room
  5. 正文加 text-autospace，.prose em 改点着重号
第三批 · 封面卡需要新写组件
  1. 新建 components/CoverCard.tsx，实现 2.35:1 蒙版封面卡（规格见 06 节 ①）
  2. PostCard.tsx 改为「有封面 → CoverCard，无封面 → TextRow」两条分支
  3. app/page.tsx 的「最近留下」区块：前 2 条走 CoverCard，其余走 TextRow
  4. GalleryList.tsx 封面放大、去边框、gap 收紧
  5. 地图标记点改墨黑，弹窗圆角改 3px

上线前检查

检查项怎么做
深色模式对比度正文 #b4b4b4 在 #111 上对比度约 8.2:1，达标；元信息 #606060 约 3.1:1，只用于非关键文字
封面卡无图兜底没有 cover 的文章必须走 TextRow，不能渲染空蒙版
页面缓存改完仍是纯 CSS 变更，不涉及 force-dynamic；但部署后 CDN 旧缓存要等自然过期
移动端<860px 时确认顶栏回来了、抽屉正常、封面卡在窄屏仍可读（建议窄屏降到 1.9:1）
热力图accent 变黑后四档自动变灰阶，检查最低档在深色模式下是否还能看见

如果只想做一步：就做第一批。换掉那 15 行 token，整个站点的气质会立刻变 —— 因为「米白 + 深绿」和「纯白 + 墨黑」是两种完全不同的审美取向，而后者正是 song.al 让人一眼记住的原因。

10 / Warmth

「看起来好冷淡」—— 诊断与暖化

这个判断是对的。原因有一半在照片，另一半在我做的几个 token 决定；而照片那一半，我自己还把它放大了。

照片是第一原因，但它只占一半

song.al 之所以不冷，是因为它的封面照片在替它承载全部温度 —— 深绿的森林、暖黄的街灯、食物的红棕色。整站唯一的彩色来源就是这些照片，界面本身越是没有颜色，照片的颜色就越突出。它的结构是「界面退让、内容发光」，不是「界面冷淡」。

而我在做设计稿时，为了「和单色主题协调」，把照片占位色块全配成了蓝灰调（#c9ccd2 → #8d939c → #565c65 这一类）。这等于先把唯一承载温度的元素抽掉，再对剩下的结果下判断 —— 这是我的方法错误，不是方案本身的必然结果。把真实照片放进去，首页的观感会完全不同。

但另外一半确实是我的选择：六个变冷的决定

冷的来源责任方影响怎么改
① 封面照片缺位，占位色块偏蓝灰内容 + 我的方法错误★★★★★封面换真实照片；占位一律改暖色
② 灰阶本身是冷灰（带蓝调）我的选择★★★★换成暖灰（见下）
③ 删掉了 --color-warm 暖棕我的选择★★★恢复，并升格为强调色
④ 栏目标题改无衬线我的选择★★★中文栏目标题回衬线
⑤ 圆角 6 → 3px、阴影全删我的选择★★回 5px，允许极轻的暖色阴影
⑥ 纯白底 + 纯黑字（最高对比）我的选择★★暖白底 #fffdf8 + 暖黑字 #241f18

其中一条值得单独讲：ueno 的灰是「冷灰」

这不是感觉，是数值。看三个色的 RGB 通道：

色值出处R / G / B倾向
#b9bbc6ueno 的元信息色185 / 187 / 198蓝通道最高 —— 偏蓝
#a8aaa2你现在的 --color-text-hint168 / 170 / 162蓝通道最低 —— 偏黄绿
#fbfbf8你现在的页面底251 / 251 / 248蓝通道最低 —— 暖白

再看 ueno 的强调色阶：它在 oklch 里的色相是 277.7°，属于蓝紫方向；chroma 只有 0.0045，肉眼几乎看不出来，但铺满整页就成了「冷」。所以「纯白 + 中性灰」并不是没有颜色，它是有一点点蓝的。你的「米白 + 灰绿」则相反，是一点点黄。这层差异极小，却正是整页气质的分水岭。

三档暖度，挑一档

不用一次决定到位。下面三档是从「几乎不改」到「接近你现在的气质」，成本和效果都不同。

档位改什么效果代价
暖度 1
只换照片		 token 一律不动，只把封面换成真实照片 立刻不冷，同时完整保留「颜色归零」的干净。改动量最小，风险最低。 依赖你的内容真有照片；没有封面的条目仍会偏冷。
暖度 2

暖度 3

图片排版模式：博文与相册

能做，而且规则比看起来简单得多。台湾行记那种排列的真相是 —— 它不是自动瀑布流，是作者手动分行。

先纠正一个误解

看到「台湾行记」里 4 张一行、3 张一行的错落排布，第一反应通常是「瀑布流」。但翻它的 HTML 会发现完全不是 —— 每一行就是一个独立的 <div class="photos"> 容器，行内每张图 flex-basis:100%，靠 flex 收缩均分成等宽。所以：

① 分行是手动写的（想 4 张一行就放 4 个 figure）；② 行内等宽平分；③ 行内等高（靠统一宽高比保证）。窄屏时整个容器从横排变竖排，一行变一列。

这个设计的好处是可控：不会出现瀑布流那种「某张图被拉得特别长」的意外，也永远不会错位。代价是你得为每组照片决定怎么分行 —— 但对个人博客来说，这反而比自动算法更符合「我想让这 7 张这么排」的意图。

图注默认藏起来。.photos figure figcaption 是绝对定位在图片底部的一条黑底白字（rgba(0,0,0,.65) + 顶部 1px 白线），默认 opacity:0，鼠标悬停才淡入。这样图片平时是干净的，需要时才出现说明。

点击开灯箱。接了 Photoswipe，靠图片上的 data-pswp-width/height 拿到原始尺寸 —— 所以 width/height 属性不是可选项。

防跳动靠写死宽高。每张 img 都带 width/height 属性（如 1120×747），浏览器提前算出占位高度，图片加载时页面不会跳。

实现要点

要点做法
防跳动每张 img 必须带 width/height（Notion 图片 URL 里通常带尺寸，取不到就在构建时读一次）。这是整节里最容易忽略、收益最大的一条。
等宽平分用 flex: 1 1 0 而不是 width: 25%。前者不用为「3 张还是 4 张」写两套 CSS，也不怕最后一行不满。
统一比例行内图片必须同比例（建议 3:2）。若混排 3:2 和 4:3，行内就会参差不齐 —— 这也是为什么 ueno 全站用同一个导出尺寸。
灯箱直接接 Photoswipe（@photoswipe/lightbox），或用你已有的 GalleryDetail 做一个轻量版本。需要原始尺寸，别只传缩略图 URL。
窄屏一行变一列。用 @media (max-width: 640px) { flex-direction: column }，不需要额外标记。
图注悬停淡入（opacity + transition .2s）。触屏没有悬停，窄屏建议改成常显的小字图注，否则手机上永远看不到说明。
性能用 Next 的 <Image> 或至少加 loading="lazy" decoding="async"。相册页一屏可能十几张图，不做懒加载首屏会很重。

一句话回答你的问题：能，而且这四种模式里最花时间的不是 CSS（加起来不到 40 行），是给图片定一个统一比例和补齐宽高属性。前者是内容规范，后者是构建流程 —— 都属于一次做完、以后一直受益的事。
